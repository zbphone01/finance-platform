# v10.31-local 版本快照

## 发布范围

- 本版覆盖历史订单上传滤重、归档订单包整包删除、已认账历史订单补归档，以及 `bill_details` 跨分区去重性能和索引瘦身灰度验证。
- 右上角系统版本号更新为 `v10.31`。
- 推荐继续使用 `deploy-update-optimized.sh` 部署。

## 跨分区订单去重

- 保留历史去重口径 `rule_id + bill_date + bill_no`，不把 `partition_date` 加入上传查询条件，避免已转移分区的订单被重复导入。
- 新增影子唯一索引 `bd_rule_bill_date_bill_no_partition_uq(rule_id, bill_date, bill_no, partition_date)`。
- 旧唯一索引 `bd_rule_partition_date_bill_no_uq` 继续保留，影子索引异常时可立即隐藏，不需要重建旧索引。
- 流式上传和兼容保留的旧上传接口共用同一去重口径，均可使用新影子索引。

## 历史订单上传滤重

- 不建立全量订单键表。
- 热区日期继续执行热表订单号滤重和文件内滤重。
- 已完成归档的历史日期先按“订单日期/匹配日期 + 规则 + 包类型”检查月归档表；组合已存在时整组忽略，不逐订单扫描归档表。
- 归档组合不存在时允许写入热表，只执行热表订单号滤重和文件内滤重；同一文件跨多个日期时逐日期独立判断。
- T+1 使用订单日期加一天定位归档日期，打包明细使用匹配日期定位归档日期。

## 归档订单包整包删除

- 按“订单日期/匹配日期 + 规则 + 包类型”删除时同时覆盖热表和所有月归档表。
- 删除归档订单前，在同一事务内恢复来源订单和关联分账明细到热表，再复用现有认账回滚、银行流水状态回算和订单包删除流程。
- 删除过程使用归档日期锁，避免与每日归档事件并发；任一步失败整体回滚。
- 删除完成后同步更新 `order_file_partitions` 和 `bill_detail_archive_runs` 快照，允许相同订单重新上传。
- 归档日期允许同时存在归档数据和重新上传的热表数据，订单明细和订单包读取会合并两个来源。

## 索引瘦身灰度

- 主表及现有 `bill_details_archive_YYYYMM` 月归档表中的下列索引改为 `INVISIBLE`：
  - `bd_status_idx`
  - `bd_original_task_idx`
  - `bd_lifecycle_package_idx`
  - `bd_operation_partition_idx`
- 本阶段不删除索引。不可见索引仍占用空间并参与写入维护，只用于验证替代执行计划。
- 后续通过 `CREATE TABLE ... LIKE bill_details` 新建的归档月表会继承影子唯一索引及候选索引的可见性；现有归档月表只调整四个候选索引的可见性，不补建影子唯一索引。
- 测试服务器1按 5,082,217 行数据测算，四个候选索引合计约 495.2 MiB；该收益要等后续正式删除索引后才能兑现。
- 测试服务器1影子唯一索引预计临时增加约 374 MiB，迁移必须安排在低峰期并提前检查磁盘空间。

## 数据库迁移

- 本版新增迁移：`migrate-v10.31-bill-details-index-canary.sql`、`migrate-v10.31-recognized-order-backfill-archive.sql`。
- 已部署 v10.30 的环境依次执行两个迁移后再部署 v10.31 代码。
- 索引迁移幂等：影子索引存在时不重复创建，候选索引已不可见时不重复修改。归档迁移通过重建事件和存储过程重复执行，不会在迁移阶段立即搬迁历史数据。

## 已认账订单归档与历史补归档

- 每日 03:10 的订单明细归档只搬迁 `match_result_id IS NOT NULL` 的已认账行，不再清空整个热表日分区；未认账订单继续留在热表供后续认账。
- 每日先处理刚满 60 天的日期，再补处理一个更早且仍有已认账热表行的日期。
- 单日按 50000 行小事务循环搬迁，复制、数量校验、运行快照更新和热表删除保持事务一致。
- 补归档按热表复合主键直接写入月归档表，不执行归档订单号滤重，也不因同日期、同规则、同包类型已有归档行而跳过。
- 这与历史订单上传滤重分工明确：上传时归档组合已存在则整组忽略；订单已经进入热表并在以后完成认账时，补归档必须继续直接搬迁。
- 主键或唯一键冲突时当前 50000 行批次整体回滚，热表行保留，`bill_detail_archive_runs.error_message` 记录错误，不使用 `INSERT IGNORE` 静默丢弃。

## 验证要求

- 迁移后确认影子唯一索引为 `VISIBLE`，四个候选索引为 `INVISIBLE`。
- 重复上传、重叠订单上传和已转移明细重新上传不得产生重复订单。
- 订单包状态、任务状态、日期状态和忽略明细查询分别由既有复合索引接管。
- 灰度观察至少覆盖 3–7 个业务日，再决定是否正式删除候选索引。

## 本地验证结果

- v10.31 迁移首次执行及重复执行均成功，确认迁移幂等。
- 主表影子唯一索引为 `VISIBLE`；主表和现有三个月归档表的四个候选索引均为 `INVISIBLE`。
- 临时执行 `CREATE TABLE ... LIKE bill_details` 验证新归档表能够继承影子唯一索引和索引可见性，验证表已删除。
- 跨分区去重查询使用 `bd_rule_bill_date_bill_no_partition_uq`，本地 `EXPLAIN ANALYZE` 实测约 `0.47 ms`。
- 四类受影响查询分别由 `bd_order_rec_item_idx`、`bd_task_status_idx`、`bd_partition_status_idx` 和 `bd_operation_status_idx` 接管。
- 上传、归档读取和归档整包删除专项测试通过（3 个测试文件、21 个用例），`npm run check`、`npm run build` 和 `git diff --check` 通过；构建仅保留既有大 chunk 和 Browserslist 数据过期警告。
- 已认账补归档在隔离库完成三阶段验证：首次只搬迁 2 条已认账行并保留 1 条未认账行；同组剩余行后续认账后可直接补归档；人为制造归档唯一键冲突时批次回滚且热表数据保留。测试数据已清理。
