# 业务规则参考

本文件保存财务对账及认账管理平台的稳定业务边界。修改前完整读取与任务对应的章节；跨领域流程同时读取所有相关章节，不要只依据单条规则局部修改。

## 阅读导航

- 功能入口和路由：功能结构
- 测试数据清理：清空测试业务数据
- 规则页面、日期汇总、人工处理和银行到账：规则维护与页面体验
- 订单文件、打包明细和多日汇总：订单明细上传与整包打包
- 分账包上传、绑定、增量认账和删除：明细分账
- 登录权限、凭证、账号和结果页面：制单、账号与结果展示
- 取消认账、状态和匹配展示：认账状态与匹配口径
- 金额校验、队列、快照增量和退款：核心认账原则
- 到账规则、基础资料、分区归档和冷热路由：基础资料与汇总

## 关键业务规则

### 清空测试业务数据

当用户明确说“清空本地”“清空测试服务器1”“清空测试服务器2”“清空 xxx 测试业务数据”时，按本节作为标准行为执行。该操作仅用于本地和测试服务器；生产环境不得执行，除非用户明确指定生产环境并再次确认。

清空范围固定为业务测试数据：

- `voucher_result_lines`
- `voucher_result_flows`
- `voucher_results`
- `order_recognition_summary_deltas`
- `order_file_recognition_summaries`
- `manual_order_work_items`
- `bill_details`
- `match_results`
- `detail_split_files`
- `order_files`
- `bank_flows`
- `recognition_date_summaries`
- `recognition_tasks`

同时清理上传缓存：

- `.upload-cache/order-files/*`
- `.upload-cache/detail-split-files/*`

保留范围固定为配置和基础资料，不得清空：

- 账号与权限：`users`、`sessions`、`role_permissions`
- 明细认账规则：`recognition_rules`、`rule_items`、`rule_item_splits`
- 到账认账规则：`income_recognition_rules`、`income_rule_splits`
- 到账信息汇总：`counterparty_records`、`counterparty_match_accounts`、`unrecorded_counterparties`
- 认账信息设置：`departments`、`projects`、`project_details`、`budget_codes`、`fundraising_platforms`、`donation_activities`
- 财务凭证配置：`voucher_template_settings`
- 凭证收款渠道：`voucher_receipt_channels`
- 银行到账账号：`bank_accounts`
- 规则更新日志：`rule_update_logs`

默认不创建备份表；如果用户要求备份，先说明备份表名称和占用风险，再执行。清空时优先使用 `TRUNCATE` 并临时关闭外键检查；如环境权限或表状态不允许，再改用按依赖顺序 `DELETE`。清空后必须复查业务表合计为 `0`，并输出保留表关键数量，确认规则、到账信息、设置和账号未被清空。

### 规则维护与页面体验

- v9.53 起，明细认账规则详情页支持按关键字、关键字字段、匹配方式搜索条件；每个条件可进入独立整页编辑，只保存当前条件及其分账设置。
- v9.53 起，明细认账规则单条件编辑沿用新建/编辑明细认账规则的交互样式，避免弹窗编辑空间受限。
- v9.53 起，入账结果的入账明细列表中，多数业务属性字段使用较小字号，预算编码恢复正常字号，提升宽表可读性。
- v9.53 起，日期汇总任务详情中的银行流水用途和附言支持换行显示，避免长文本被截断看不全。
- v9.53 起，删除整日日期汇总任务时显示处理进度，并在当前删除完成前禁用所有日期汇总删除操作，避免用户误以为页面无响应或重复删除。
- v9.53 起，前端页面改为按路由懒加载；后端构建时外置常用服务端依赖，显著缩小首屏 JS 和 `dist/boot.js` 体积。部署仍使用 `deploy-update-optimized.sh`，但运行环境必须保留/安装 `node_modules`，不能只上传 `dist` 目录运行。
- v10.06 起，认账及分账列表手动点击“开始认账”要使用弹窗展示 `n/4` 步骤和执行结果，不再使用浏览器确认框或只用 toast 提示。
- v10.07 起，手动点击“开始认账”先按当天流水状态筛选候选任务：未认账流水同步执行到账认账，有订单明细的未认账、部分认账、差异大任务进入明细认账队列；已完成、处理中和无流水任务应跳过。明细认账队列任务成功或失败后必须刷新日期汇总缓存，避免日期汇总停留在“认账执行中”。
- v10.10 起，认账及分账列表和日期汇总详情顶部状态必须共用 `recognition_date_summaries.status`；前端状态文案、颜色和图标从公共配置读取，避免列表和详情显示不一致。v10.77 起，详情接口不再读取前刷新日期汇总，上传、认账、取消、删除等写路径必须在业务更新完成后刷新缓存。
- v10.10 起，认账及分账列表中的 `差异大` 状态只作为状态标签展示，不再点击打开差异信息弹窗。
- v10.10 起，日期汇总订单明细列表不再提供 `搜索订单金额` 输入框，保留状态筛选和分页。
- 日期汇总银行流水的差额金额调整流程优先从当前明细包查找单条等额或多条组合等额的建议忽略订单；当前明细无法直接抹平差额时，再引入同一明细认账规则的 T+1 已忽略订单，按“建议忽略金额合计 - 建议转移金额合计 = 当前差额”查找净额组合，例如差额 `0.41` 可用忽略 `2.00`、转移 `1.59` 抹平。确认时服务端必须重新校验两组订单的规则、状态、包类型和净额；忽略及转移成功后自动将被点击流水对应的任务重新加入明细认账队列。同日汇总匹配的全部同日流水已经绑定在一个认账任务内，因此只将该任务显示为认账执行中并只提交一次队列，不扩大为整日其他无关任务重跑。
- 日期汇总银行流水的普通部分认账待认账金额支持点击查找同明细认账规则的 T+1 已忽略订单；如果被点击流水对应任务存在尚未认账的待拆分订单，推荐转移金额按“待认账金额 - 待拆分订单金额”计算，只按扣除后的金额查找单条等额或多条等额组合。同日汇总匹配直接汇总当前聚合任务内的待拆分订单。待认账金额与待拆分订单金额一致时不推荐转移并提示“无推荐转移订单，请进行明细分账完成认账”；待拆分订单金额大于待认账金额时同样停止推荐并要求先完成明细分账。弹窗展示待认账、待拆分、推荐转移和已选金额，也可人工选择，但所选金额合计必须等于当前推荐转移金额；候选查询与确认提交都必须重新读取待拆分金额。确认后将明细定向转移到被点击流水任务，保留原订单日期和原归属快照；跨日转移同步更新 `partition_date` 及 `order_file_partitions`。转移完成后只对未认账转入明细执行增量认账，不删除或重建已有入账结果。
- T+1 转入订单执行增量认账时，规则刷新范围必须同时包含当前订单和 `operation_status = 'transferred'` 的转入订单；转入订单引用的旧 `rule_item_id` 已被规则编辑删除时，应先重置并按当前规则重新匹配，不能因条件 ID 失效而静默跳过。
- 订单明细转移只支持 `T+1`；`打包明细` 不进入部分认账转移候选，日期汇总明细和“人工处理订单”列表中的已忽略订单也不允许对打包明细执行转移，后端所有转移接口必须重新校验包类型。
- v10.12 起，银行流水表保存 `bank_name`，上传银行到账时按表头自动识别广发银行、工商银行和中国银行；工商银行流水只支持手动认账。
- v10.47 起，广发银行到账文件上传时读取交易明细表头之前的本方 `账号`，按文本保存到 `bank_accounts`，并通过可空的 `bank_flows.bank_account_id` 关联流水；`bank_flows.bank_name` 继续保留作为银行来源和无账号文件的兜底。工商银行和中国银行通过 `财务凭证信息 / 银行/到账账号` 手工维护账号和凭证名称，并可设置每家银行的默认账号；缺少本方账号的上传流水关联当前默认账号，未配置默认账号时允许保持空关联。上传采集账号号码不可编辑，手工账号可编辑；制单汇总行的银行账户读取关联账号的凭证名称。
- v10.63 起，广发银行到账文件同时读取 `收入` 和 `支出`：收入按正数、支出按负数统一保存到 `bank_flows.income`，金额为 0 的行不入库。日期汇总的银行到账金额和已认账金额按正负数净额汇总，银行流水列表继续在 `收入` 列展示支出负数；支出流水不参与订单明细匹配，只进入到账规则或手动认账。支出认账、分账、管理费和入账结果均保持负数方向，认账状态与剩余可认账金额按单笔流水方向计算，不能用收入与支出相抵后的任务总额替代单笔判断。
- v10.75 起，日期汇总的银行流水列表按 `bank_flows.income` 正负数在“收入 / 支出”之间服务端分页切换：正数为收入并继续参与到账规则、手动认账和明细认账，负数为支出且只读展示，不再进入自动到账认账、认账时填写、手动认账、取消认账或新制单。历史支出认账结果和凭证不自动删除或回滚，只在支出列表保留历史操作痕迹并不提供新认账。支出不作为任务和日期汇总的待认账条件；`bank_flow_total` 继续保留正负净额，日期汇总详情的“银行流水收入总额”读取 `recognition_date_summaries.bank_flow_income_total`，只汇总正数收入；`bank_flow_count` 同样只统计正数收入流水条数。收入流水的认账状态在认账或其他认账结果变更完成时写入 `bank_flows.recognition_status`，日期详情列表直接按该状态展示；任务执行中可临时显示“认账执行中”，任务收尾后再刷新一次列表。v10.77 起，收入流水的已认账条数同步缓存到 `recognition_date_summaries.recognized_bank_flow_count`，顶部“认账情况”分子直接读取该字段。
- 日期汇总银行流水在主列表页签下按“广发银行 / 工商银行 / 中国银行”切换，收入/支出切换与银行切换同一行居右；后端必须按日期任务范围、`bank_name` 和金额方向先过滤再分页、计数。顶部日期汇总卡片继续读取整日 `recognition_date_summaries` 缓存，不随银行切换重算。广发银行列表列顺序为 `ID-流水号-交易时间-收入/支出-对方账号-对方户名-摘要-备注-附言`；工商银行为 `ID-流水号-交易时间-转入金额-对方单位-对方账号-用途-摘要-附言`；中国银行为 `ID-付款人账号-付款人名称-交易时间-交易金额-交易流水号-摘要-用途-交易附言`，状态、差额和操作列仍按现有条件追加。
- 三家银行的识别和认账字段统一保存在 `bank_flows`：银行、流水号、交易时间、正负收入、对方账号、对方户名、摘要、用途/备注、附言/交易附言分别使用 `bank_name`、`reference_no`、`transaction_time`、`income`、`counterparty_account`、`counterparty_name`、`summary`、`purpose`、`post_script`。广发“备注”、工商和中国银行“用途”统一写入 `purpose`；不新增重复的支出或备注列。到账信息匹配条件文案同时展示各银行原始名称，但仍读取上述统一字段。
- v10.81 起，新增收入流水在上传写路径统一匹配全部到账信息及其启用的多组匹配条件，并把唯一最高精度结果固化到 `bank_flows.matched_counterparty_id + arrival_match_status`；最高精度并列时保持 `unmatched` 并在上传结果提示歧义。匹配为“到账认账”时只执行该到账信息关联的启用规则，匹配为“明细认账”时保持待认账，T+1、打包明细、同日汇总和多日汇总后续只按固化到账信息 ID 查找流水，不再用流水原字段重新匹配。`recognition_status` 继续单独固化实际认账进度；收入列表只据两个固化状态映射“待认账/未认账”，不增加到账信息列，也不在读取时补匹配或写回。
- v10.83 起，`counterparty_match_accounts` 是到账匹配条件唯一来源且不限制组数，`counterparty_records` 不再保存银行、账号、户名、摘要、用途和附言条件。新增、编辑和批量记录必须在事务内保证每个主记录至少一组有效启用子项；匹配、重新匹配、未记录滤重和所有明细模式禁止回退主表条件。需要保存单组展示快照时固定取启用子项中 `sort_order, id` 最小的一组。
- v10.84 起，银行流水上传先完成滤重、到账信息匹配和 `matched_counterparty_id + arrival_match_status` 固化，全部新增流水入库后只读取一次启用的 `income_recognition_rules` 及其 `income_rule_splits`。本次新增且匹配为“到账认账”的正收入流水按 ID 升序每 100 条一个事务批量生成 `match_results` 并更新流水状态，不进入数据库重任务队列，也不扫描历史流水；“认账时填写”只固化 `income_rule_id` 并保持未认账。任一批失败时该批回滚、后续批次停止，已上传流水和此前成功批次保留，页面必须提示未完成数量并允许后续从日期任务重新开始认账。
- 待认账流水允许使用独立的“管理银行到账匹配”权限取消匹配；服务端必须在事务内确认流水仍未认账、任务未执行、无入账结果、无凭证、无多日匹配组且任务未绑定订单包或明细分账包，成功后清空到账信息和待填写到账规则并写入 `arrival_match_status = cancelled`，禁止后续自动认账。未认账流水可手动“重新匹配”一次当前配置；仍无匹配或存在歧义时保持未认账，唯一匹配时按到账认账或明细认账分支继续处理。取消自动到账认账结果时同样写入 `cancelled`，避免刚取消后再次自动命中。管理员始终允许该操作，运营和财务默认关闭。
- 中国银行到账文件按双语表头识别，只入库 `交易金额[ Trade Amount ]` 为正数的行。流水号读取 `交易流水号[ Transaction reference number ]`，交易时间由 `交易日期[ Transaction Date ]` 与 `交易时间[ Transaction time ]` 拼接，收入读取交易金额；对方账号、对方户名、对方开户行分别读取付款人账号、付款人名称、付款人开户行名，交易行所固定为空；摘要优先读取 `备注[ Remarks ]`，备注为空或只有空格时回退读取 `业务类型[ Business type ]`；用途读取 `用途[ Purpose ]`，附言读取 `交易附言[ Remark ]`。文件顶部查询账号不自动采集为本方账号。
- v10.12 起，银行直捐手动认账预算编码后必须提供 `NC项目名称` 下拉，并在入账结果中保存到 `match_results.income_project`。本版不自动修复历史为空的数据。
- v10.13 起，手动认账选择 `银行直捐` 且收入类型为 `利息` 时，反馈类型、地区、匿名、会员姓名和管理费均可不填；支出资金来源无需填写，前后端固定保存为 `非限定性-利息收入`，管理费按空值/0 落库。
- v10.63 起，手动认账的收入类型支持 `订单退款`。认账金额为负数时，新建分账默认选择 `订单退款`，但不覆盖用户已经手工选择的收入类型；`订单退款` 与 `捐赠收入` 使用相同的捐赠来源及属性必填规则，按互联网募捐平台、银行直捐或拍卖切换对应字段。手动生成的订单退款保留捐赠来源并可按相同属性继续修改；历史自动退款未保存捐赠来源时继续沿用原平台退款属性，避免影响历史数据。
- v10.64 起，手动认账在已选择支出资金来源后选择或切换反馈类型时，必须保留已选捐赠活动和到账户名，只更新支出资金来源中的反馈类型片段；不得清空整个支出资金来源。会费收入继续使用固定资金来源，不参与该联动。
- v10.63 起，到账认账生成的 `订单退款` 支持单独正常制单，使用 `捐赠收入-到账认账模版`，入账金额、分账金额、项目资金和管理费保持负数写入凭证行。到账退款按 `rule_item_id` 为空且 `order_detail_count_snapshot = 0` 识别；手动明细退款和自动明细退款继续沿用原有随捐赠收入制单规则，不能误判为到账退款。

### 认账状态与匹配口径

- `认账及分账` 日期详情是银行流水取消认账的统一入口；已认账或部分认账流水只有在取消范围内全部订单明细仍位于热区时才显示取消认账操作，`已认账/已制单` 或包含已归档订单明细时不显示。普通流水取消该到账关联的全部认账结果，同日汇总匹配从任意一笔到账发起都取消整个同日汇总任务，多日汇总匹配从任意一笔到账发起都严格按已确认匹配组取消整组结果，不得扩大到同日期或同规则的其他流水。整组取消必须在事务及归档日期锁内只回滚热区自动明细、手动明细、到账规则和手动到账结果，不再扫描或恢复月归档表；确认查询和提交都必须重新校验归档、锁定与凭证状态，任一目标结果包含归档明细、已锁定或已生成凭证时整组禁止取消。若结果记录的订单明细数大于热区实际关联数，必须先区分真实归档与订单包已删除造成的残留：存在结果归档标记或对应日期已完成归档运行时继续禁止取消；没有归档证据、凭证和锁定时按孤儿结果提示，并允许在银行流水统一入口事务化清理残留结果，不能错误提示为“存在已归档订单明细”。v10.62 起，取消事务提交成功后接口立即返回并关闭确认弹窗，任务状态和日期汇总等派生状态在后台最多重试三次；前端立即刷新并在短延迟后复查。若请求报错但复查确认认账结果已经删除，按取消成功关闭弹窗，不得让用户因提交后的刷新异常重复取消。

### 核心认账原则

- 入账结果来源包括明细认账、到账认账和手动认账。
- 流程维护约定：涉及本文档已记录的显示优化、交互优化、性能优化或已调整业务流程时，即使有更优逻辑建议，也必须先向用户确认，不得直接改动既有优化边界。
- 所有订单明细认账都有统一前置条件：只有匹配到账总额或剩余可认账金额大于等于本次待认账净额（当前订单包未认账净额加当前任务转移订单未认账净额）时，才允许开始明细认账；否则只计算差异金额并提醒，不生成入账结果、不把订单明细或银行流水标记为已认账。
- 因为已有上述前置条件，订单明细认账执行阶段不再需要用单条订单明细金额逐条试探或匹配到账流水余额；执行时只按明细认账规则条件汇总入账。入账执行期间，对应银行流水展示为“认账执行中”；入账完成后，相关银行流水和订单明细同步变更为已认账。
- v10.39 起，普通明细认账存在转移订单时，仍只使用一个队列任务：前置金额校验一次性汇总“当前订单包未认账净额 + 当前任务转移订单未认账净额”，校验通过后先按原有逻辑认当前订单包，再认转移订单。第二阶段必须复用任务开始时的可认账金额基准和已选目标流水，不重新校验剩余金额、不重新选择流水；两个阶段全部结束后再统一更新流水、任务和日期汇总状态。明细分账包增量认账保持独立入口，不进入该两阶段流程。
- v10.39 起，认账金额比较和银行流水状态判断统一换算为整数分后执行，不保留 `-0.01`、`+0.01` 等容差：累计认账 `999` 分、到账 `1000` 分时为部分认账，累计达到或超过 `1000` 分时才为已认账；同日汇总按固定流水顺序用累计已认账分值依次覆盖并计算各流水状态。
- 明细认账金额判断只允许明确 `0.00` 金额不生成入账结果；`0.01` 等小额正数必须正常入账，负数退款明细也必须保留继续生成入账结果的路径，不得用小额阈值或 `<= 0.01` 一类判断跳过。
- 当前限制：订单金额明确为 `0.00` 的订单明细不生成入账结果，也不会回写 `match_result_id`；即使其他非 0 明细金额已与银行到账金额匹配，订单明细列表中仍可能保留 0 元未认账明细。后续若要求订单明细全量闭环，需要单独迭代 0 元明细的认账标记或展示口径。
- v9.52 起，订单明细上传预匹配固定先执行 `等于`、再执行 `包含`；`等于` 条件按字段和关键字建立快速索引，用户录入顺序不再影响精确规则优先级。
- v9.52 起，手动开始认账补匹配未匹配明细时，同样先跑 `等于`、再跑 `包含`，随后只处理已匹配且未入账明细。
- v9.52 起，认账队列支持同一任务、同一认账范围去重；重复入队会合并等待者和执行选项，避免连续上传或重复点击导致等待中的任务重复执行。v10.69 起，普通认账、不同 `detail_split_file_id` 的明细分账增量认账必须使用不同队列身份并保持串行，禁止合并后丢失分账包范围。
- 数据库重任务除保持当前进程内 FIFO 串行外，还必须通过 `crossAppDbHeavyLock` 取得按数据库环境隔离的 MySQL 共享命名锁，避免认账平台多实例或票据系统开票查询并发压库。`recognition` 类型任务必须先取得认账优先锁、再等待共享锁；普通重任务取得共享锁后必须复查认账优先锁，发现已被占用时立即释放共享锁并短暂等待后重试，不能依赖 MySQL 的抢锁顺序。票据系统的订单冷热搬运、孤儿清理和无单号索引扫描均必须沿用该协议，每次只执行一个有界批次后释放共享锁，让已排队认账先执行。锁必须使用独立连接并在任务结束后按相反顺序释放，连接异常退出时依赖 MySQL 自动释放，不得把命名锁放到普通连接池事务中。
- 订单明细包删除也属于数据库重任务，后台进度删除和兼容直连删除入口都必须进入 `dbHeavyQueue` 并取得跨应用共享锁，与订单上传和认账串行；等待期间显示“正在等待认账任务完成”。同一包的整包删除与单文件删除使用不同去重键，不能把不同删除范围合并成同一任务。
