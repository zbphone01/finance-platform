# 性能与存储红线

本文件保存列表、汇总、大文件、批量处理和冷热数据相关的稳定性能边界。修改这些路径前完整读取本文件，并同时读取业务规则参考中的对应业务章节。

以下优化来自历史版本说明，后续迭代不要为了修统计口径或展示问题而改回实时大表扫描。

- v9.34 起，`认账及分账` 日期列表和日期详情顶部汇总必须读取 `recognition_date_summaries` 缓存；不要在页面打开时实时聚合 `bill_details`、`bank_flows` 或 `match_results` 大表。
- v9.34 起，日期详情默认只展示汇总，切到 `订单明细` 页签也先展示缓存汇总；只有点击 `查看具体明细` 后才读取订单明细分页数据。
- v9.34 起，上传明细、认账、删除、忽略、转移等写路径负责刷新对应日期汇总缓存；读路径不要用实时重算弥补缓存问题。
- v9.36 起，`订单明细包` 列表必须基于 `order_files` 汇总字段展示条目数、匹配数和状态；不要从 `bill_details` 明细大表实时聚合列表。
- v9.36 起，订单明细包列表依赖 `order_files` 汇总字段和索引加速；打开列表不应随单个数据包内明细量明显变慢。
- v10.64 起，人工处理订单列表、三类状态汇总和规则选项必须全部读取 `manual_order_work_items`；忽略、转移、认账、取消认账、取消操作和订单包删除等写路径负责同步或删除投影，读路径不得回退为枚举热表与全部月归档表。
- 订单明细包“详情”列固定读取上传结果快照；忽略或转移后禁止为了更新列表而重新扫描大明细表，也禁止在状态变更的增量路径中加减上传条数、收入或退款。
- v9.38 起，订单明细上传必须保留分片上传、流式解析、批量入库和上传阶段预匹配；不要改回前端一次性上传或上传后再无条件扫描大表匹配。
- v10.80 起，明细分账上传的子订单滤重必须与现有 5000 行批次对齐：每批用唯一键批量抢占 `detail_split_order_dedup_keys`，再一次性读取本批键的归属并只写入获胜行；禁止逐行查重，也禁止把整文件子订单号长期保存在无界内存集合中。滤重表承担跨热表、归档表和分账包的业务唯一性，不能改回扫描 `bill_details` 或为 `bill_no` 新增索引。
- v10.59 起，预匹配认账汇总必须利用上传过程中已经解析的数据流在内存中累计，只写规则条件级小结果；只有 `INSERT IGNORE` 实际写入条数与待写条数不一致时才允许回退扫描该订单包核对快照，并把认账汇总标记为无效。
- v10.78 起，退款订单值和可选收支方向值必须在上传任务开始时各归一化一次；逐行只读取一次共用判断字段并做最多两次精确比较，仅在命中直接退款或收支方向值时读取必要金额。禁止逐行解析配置、构造集合或查询数据库，也不得扩大 `order_file_id + rule_item_id + 是否退款` 的预匹配汇总分组。
- v10.59 重发版起，新上传 T+1 首次自动认账只有在全部订单包汇总有效、汇总条数与订单包已匹配数一致、规则条件未变化、没有既有明细认账结果或多日汇总范围时才允许走快路径。v10.60 起，完整的来源扣减和目标转入增量可以加入该快路径；认账前金额校验和认账后任务状态读取任务/订单包快照、条件汇总及增量，不得再次按整包执行已认账、未认账 `SUM/COUNT`。任一校验失败继续回退原明细查询。
- 能直接定位 `order_file_id` 的当前订单包读取和批量写回应同时读取 `order_file_partitions` 并补充 `partition_date` 进行分区裁剪；订单号去重仍保持跨分区查询，不得把该裁剪错误复用到上传去重。
- 票据平台订单开票不为 `bill_no`、`invoice_other_order_no_1`、`invoice_other_order_no_2` 新增查询索引；查询必须以 `bill_date >= 上海当前月月初减 24 个月` 为硬边界，并在跨应用数据库重任务锁内执行有界批次。认账平台历史字段回填同样只处理该范围，热表和月归档表每批最多 50000 行，禁止一次性更新全部历史明细。
- 自动认账保留 `recognition-performance` 的 `precheck / result-writes / finalize` 三段日志。大订单复测先确认 `fastUploadSummary` 或 `fastSummaryDeltas` 是否为 `true`，再按分段耗时区分前置统计、结果写回和最终状态刷新。
- v10.79 起，明细分账增量认账的批量写回必须按任务 `partition_date` 裁剪到单个分区，并强制使用已有 `bd_rule_detail_split_status_idx`；不得重新依赖可能选择 `bd_rule_detail_split_status_idx ∩ bd_task_status_idx` 的 `index_merge`，也不得为该问题新增 `bill_details` 索引。
- v10.79 起，归档只在原 50000 行批次选择中增加 `match_result_id IS NOT NULL`，禁止为约每日 10 条的未认账留存增加逐行关联子查询或新索引。过期未认账明细随日分区合并进 `p_late`；迟到补归档只枚举仍有已认账明细的日期，不能让长期未认账日期阻塞后续归档。
- v9.39 起，日期详情页只挂载当前页签；不要在默认打开银行流水时同步加载订单明细或入账结果列表。
- v10.75 起，日期详情的银行流水“收入 / 支出”切换必须在 `task.getFlows` 中按金额方向分页和计数，不能先分页再由前端过滤；顶部“银行流水收入总额”和流水条数分别读取 `recognition_date_summaries.bank_flow_income_total` 与只统计正数收入的 `bank_flow_count`，由上传、删除和状态刷新等写路径维护，禁止打开详情时实时扫描全部银行流水。银行流水认账状态同样由认账、取消认账及任务收尾等写路径维护，`task.getFlows` 只读取已保存状态，禁止在打开列表、切换方向、翻页或轮询时重算并写回。支出列表必须走轻量只读分支，只查询负数流水分页、总数和删除锁定依赖，不得查询认账结果、凭证、收入规则或同日/多日汇总状态。v10.77 起，日期详情的已认账收入流水条数读取 `recognition_date_summaries.recognized_bank_flow_count`；`task.getById` 只读汇总缓存，不得因页面打开实时刷新日期汇总或聚合 `bank_flows`。
- v10.81 起，银行到账上传必须在单次上传开始时各批量读取一次 `counterparty_records` 和启用的 `counterparty_match_accounts`，逐条流水只做内存匹配，禁止逐流水重复查询到账信息配置。v10.83 起主表批量查询仅承载到账别称、认账类型等业务元数据，匹配条件只允许来自启用子项，不得为兼容缺失子项重新增加主表条件读取。明细认账候选必须直接使用固化的 `arrival_match_status = matched + matched_counterparty_id` 限定；T+1 和同日路径继续利用日期任务范围，打包明细最早到账继续按既有状态、日期、交易时间和主键做最多 50 页的有界扫描，取消匹配和重新匹配按流水主键操作。首版不为 `bank_flows` 增加组合索引；只有真实执行计划或慢查询证明现有边界不足时，才单独评估索引，禁止为预估场景持续叠加索引。
- v10.84 起，银行流水上传的到账认账只能处理本次新增并已固化到账信息 ID 的正收入流水：全部流水入库后一次读取启用的到账认账规则和分账，在内存建立到账别称、规则及分账映射，再按流水 ID 每 100 条一个事务批量写入 `match_results` 和流水状态。禁止在上传循环内逐流水重新读取规则、分账、到账信息、既有结果或刷新日期汇总；任务状态和 `recognition_date_summaries` 必须在批次完成或失败收尾后按受影响任务统一刷新。该上传批量路径不进入数据库重任务队列，不得因此扩大为扫描历史未认账流水。
- v9.39 起，手动认账所需的大字典树只在选中未认账流水后加载；不要为只读列表提前拉取部门、预算编码、项目、公益平台、捐赠活动树。
- v10.73 起，“上传订单明细”的规则选择必须读取专用轻量摘要，只返回有效规则的 ID、名称、条件数量、明细包类型和匹配方式；不得复用会连带创建人、全部规则条件及分账明细的规则管理列表。候选在上传弹窗打开时加载并短期缓存，前端使用名称或 ID 搜索，不能恢复最多 100 条的静默截断。
- v9.45 起，入账汇总必须在数据库聚合；不要让前端拉明细后计算汇总。
- v9.50 起，到账认账规则列表首屏只返回规则摘要和分账数量；编辑、复制时再按规则 ID 加载完整分账。
- v9.52 起，同日汇总明细认账按规则条件汇总生成入账结果；不要改回按单条明细金额逐条扣减到账余额。
- v9.52 起，单笔匹配先统计命中金额和条数，达到大批量阈值后按条件批量回写；不要把大批量路径改成逐条更新。
- v9.53 起，前端页面按路由懒加载；部署仍使用 `deploy-update-optimized.sh`，运行环境保留 `node_modules`，不要退回首屏全量打包。
- v9.65 起，明细分账包列表必须读取快照字段展示未匹配、待认账、已认账数量；上传完成和拆分认账完成后由写路径刷新快照，不要在读路径实时扫描分账明细。
- 维护原则：如果统计口径新增字段，例如待拆分数、未认账数、制单数，应优先扩展缓存表或汇总字段，并在上传、编辑、认账、删除、忽略、转移、恢复等写路径刷新缓存；不要在列表或详情首屏查询中临时实时聚合大明细表。
