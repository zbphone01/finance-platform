# v10.60-local 版本快照

## 发布范围

- 新增轻量表 `order_recognition_summary_deltas`，只记录 T+1 订单忽略、恢复、转出和转入对认账汇总造成的变化，不复制订单原始字段。
- 来源订单包按 `source_deduction` 保存扣减；目标认账任务按 `target_transfer_in` 保存转入。每种变化同时维护总数量/净额和 `rule_item_id + 是否退款` 分组。
- 忽略、恢复、转移和取消转移时，明细状态、任务/订单包计数、分区定位及增量写入处于同一数据库事务，任一步失败整体回滚。
- 来源上传快照有效且增量完整时，认账使用“上传快照减来源扣减”；目标转入增量覆盖完整时，使用目标增量完成金额校验及收入/退款分组。
- 快路径严格校验文件总数、状态分组数、转入热表未认账数量及当前规则条件。历史变化、覆盖不完整、规则条件失效、补匹配、明细分账或多日汇总继续回退 `bill_details`。
- 使用上传快照或目标增量生成入账结果前先使缓存失效。认账中断后重试会回退明细表，不复用可能已覆盖部分结果的缓存。
- 每日订单明细归档的 50000 行事务中，同步使来源上传快照失效并删除上传快照、来源扣减和对应目标转入增量。
- 已归档明细的恢复或转移认账不在本版本范围内，继续保持现有只读/手动认账约束。
- 右上角系统版本号更新为 `v10.60`。
- 部署包：`releases/finance-platform-v10.60-local.tar.gz`，包含本地验证通过的预构建 `dist/`。

## 数据库、依赖与配置

- 必须先执行 `migrate-v10.60-order-recognition-summary-deltas.sql`，创建增量表。
- 随后执行 `migrate-v10.60-archive-order-recognition-summaries.sql`，替换 `archive_bill_details_day`，把快照和增量清理纳入归档批次事务。
- 增量表主键包含增量类型、来源订单包、目标任务、规则、归属日期和汇总维度；来源读取使用 `orsd_source_idx`，目标读取使用 `orsd_target_idx`。
- 增量表通过 `order_file_id` 外键关联 `order_files`，删除订单包时自动级联删除。
- 迁移不扫描、不回填历史 `bill_details`；历史忽略和转移继续通过覆盖校验进入原明细查询。
- 本版本不新增 npm 依赖、环境变量或运行配置。

## 认账安全边界

- 来源快照只有在 `recognition_summary_valid = 1` 且“有效总数 = 已匹配 + 未匹配 + 待拆分”时可用；分组数量还必须等于当前已匹配数量。
- 目标转入增量的总数量必须等于热表中当前任务、规则、日期下未认账转入明细数量；分组数量不能超过总数量。
- 增量扣减失败、缺少反向记录或出现数量不一致时，来源快照立即失效或目标增量立即删除，后续认账回退明细表。
- 全部明细被忽略、任务汇总归零时，金额检查读取“上传快照减增量”的有效总数，不得恢复使用上传时原始总数。
- 新增会改变 T+1 明细可认账范围的写路径时，必须同步维护增量或明确使上传快照失效。

## 风险与回退

- 增量只优化少量忽略/转移后的认账统计；最终给 `bill_details` 写入 `match_result_id` 的批量更新仍会访问订单明细。
- 目标增量快路径仍执行一次有索引范围的转入数量覆盖检查；它只统计转入明细，不对整包明细做规则分组。
- 历史订单没有增量记录，不会自动补数据，首次相关认账会回退原逻辑。
- 普通代码回退可恢复 v10.59 部署包并保留 `order_recognition_summary_deltas` 空闲表；旧代码不会读取该表。
- 普通回退不要直接删除增量表，因为 v10.60 的归档过程依赖该表。若必须删除结构，应先在维护窗口恢复 v10.59 对应的 `archive_bill_details_day` 定义，再删除增量表。
- 自动归档清理与当前归档批次同事务执行；如果清理 SQL 失败，当前批次不会删除热表明细。
